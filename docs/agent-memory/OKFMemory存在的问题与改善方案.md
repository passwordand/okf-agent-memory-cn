# OKF Memory 存在的问题与改善方案

日期：2026-09-11  
适用环境：本机 Windows，OKF Agent Memory v0.1.5，OpenCode / Codex / WorkBuddy 共用现有接入  
文档状态：评估与待实施方案；本次未修改引擎、客户端配置或迁移项目数据

## 1. 结论与目标

**保留现有 OKF 记忆，优先修复中文检索，并简化项目 / 全局库的访问方式。目前没有证据表明需要迁移整个记忆系统。**

当前问题不是“OKF 安装失败”，而是三件事叠加：

1. **引擎缺陷**：v0.1.5 搜索分词直接丢弃中文，纯中文查询无法工作。
2. **接入方式与使用范围不匹配**：当前 MCP 默认库与允许访问的根目录在启动时确定，无法直接覆盖分散在 C、D、E 盘的项目库与全局库。
3. **本机定制流程不完整**：固定进度文件、自动全局回退和压缩注入是额外搭建的机制，其中存在缺文件和作用域混淆。

用户目标是：**快速接入、稳定好用、日常不需要记路径或操作命令、尽量少维护。** 因此本方案不以双 MCP、云端记忆、看板、自动同步或更换系统为默认方向。

## 2. 当前部署与官方用法

### 2.1 本机已确认的部署

| 组件 | 当前情况 |
|---|---|
| 引擎 | `C:\Users\zhou\.config\agent-memory\bin\okf.exe`，v0.1.5 |
| MCP wrapper | `C:\Users\zhou\.config\agent-memory\mem-mcp.js` |
| 全局库 | `C:\Users\zhou\.config\agent-memory\knowledge` |
| 项目库 | 已迁移的 13 个 `knowledge/`，分布于 C、D、E 盘 |
| Codex 接入 | 单个 `okf-memory` 条目，通过 Node 启动上述 wrapper |
| 默认库选择 | 从 wrapper 启动时的 cwd 向上找 `knowledge/index.md`；找不到就选全局库 |
| OpenCode 压缩注入 | 从当前目录向上找 `knowledge/progress/current.md`；找不到就读取全局进度 |
| 双 MCP | 桌面 v1.2 方案已描述，但本次核查的实际 wrapper 与 Codex 配置仍是旧版单 MCP |

本次已成功通过 MCP 读取全局记忆。先前对 13 个迁移项目库执行的严格校验均通过，未发现这些项目库的格式或链接损坏。格式校验不等于内容准确、检索可靠或进度完整。

### 2.2 官方实际推荐

官方将 OKF 定位为存放在项目仓库 `knowledge/` 中的持久知识，标准流程为：

1. 搜索已有知识。
2. 完成工作。
3. 用 `create` / `update` 保存重要决策、发现和事实。
4. 执行 `validate` 校验。

官方提供两种接入路径：

- **CLI**：Agent 调用 `okf search/show/create/update`，指定知识库路径；入门文档对 Codex / Gemini CLI 明确给出这种方式。
- **MCP**：直接运行 `okf mcp /path/to/project/knowledge`；官方示例不需要额外 Node wrapper。

`bootstrap` 可生成知识库、Skill、`AGENTS.md` 和便利命令。以下内容属于本机定制，不能当成官方强制要求：

- 项目库缺失时自动回退全局库。
- 每个项目固定维护 `progress/current.md`。
- 会话压缩时自动注入该进度文件。
- 项目 / 全局双 MCP 接入。

## 3. 已确认问题及影响

### P1-01：中文搜索词被直接丢弃

**性质：引擎实现缺陷。优先级：最高。**

官方 v0.1.5 的 `pkg/okf/search.go` 中，`tokenize()` 仅保留 ASCII 英文字母和数字，其他字符都作为分隔符。纯中文查询最终没有任何搜索词，搜索函数直接返回空。

本机实际查询结果：

| 查询 | 结果 |
|---|---|
| `记忆` | 空 |
| `迁移` | 空 |
| `记忆库` | 空 |
| `记忆 进度` | 空 |
| `OKF` / `MegaMemory` | 可找到相关概念 |

上述中文内容确实存在于知识库中。因此这不是编码配置错误，也不只是“不支持语义搜索”。混合查询能命中时，也可能只是其中的英文起了作用。

**影响**：旧知识查不到、误以为没有记录、重复建概念、“写前先搜索”失去可靠基础。

**不能解决问题的做法**：仅在描述中补中文同义词、重启 MCP、重新部署同版本。

### P1-02：项目 / 全局访问受当前服务根目录限制

**性质：官方 MCP 边界与本机跨盘布局不匹配，叠加 wrapper 的静默回退。**

本次通过全局 MCP 指定 `E:\UnityProgram\moxian\knowledge` 读取进度时，收到 `Path traversal denied`，提示目标超出 `C:\Users\zhou\.config\agent-memory` 服务根目录。

需要准确区分：

- 一个 MCP 服务并非绝对只能访问一个库；它可以通过 `bundle` 参数访问允许根目录内的其他库。
- `OKF_MCP_ROOT` 可以配置根目录，但该版本的路径校验不能用一个普通 Windows 根目录同时覆盖不同盘符的原始路径。
- 在聊天中提到新项目，或在另一个终端执行 `cd`，不会改变已运行 MCP 服务的默认库与根目录。
- wrapper 找不到项目库时会静默回退全局库。这是明确存在的行为；尚未证明所有客户端启动 cwd 都错误，也未确认真实项目数据已经因此写错。

**影响**：Agent 知道项目库存在，却无法通过当前 MCP 读取；缺库项目的写入可能落到全局。用户不得不理解服务作用域，增加使用成本。

### P2-01：固定进度恢复流程缺少必要数据

**性质：本机定制流程未完成，不是 OKF 格式或安装损坏。**

已核查的 13 个迁移项目中，只有 moxian 存在 `progress/current.md`，其余 12 个缺失。迁移了旧概念，不代表已经整理出可信的当前进度。

**影响**：按现有规则在会话开头直读进度时，多数迁移项目无法完成；但其知识概念本身仍可存在并通过校验。

### P2-02：压缩注入可能把全局进度标成项目进度

**性质：本机 OpenCode 插件逻辑缺陷。**

插件找不到项目进度时读取全局 `progress/current.md`，但输出标题始终为“项目进度”。另外，插件按“进度文件存在”选库，wrapper 按“知识库索引存在”选库，两套规则不一致。

**影响**：续接上下文可能包含其他作用域的进度，Agent 将其误当作当前项目状态。此结论来自代码路径核查，并不表示已经观察到所有会话都发生错误回答。

## 4. 不应扩大成“硬伤”的事项

- **13 个项目库校验通过**：不能把缺少自定义进度文件说成迁移库全部不可用。
- **全局进度为孤立概念**：先前校验显示 `is_conformant=true`、`gate_passed=false`，`progress/current` 为 orphan。这是需要修的索引关联问题，但不等于记忆丢失。
- **跨客户端并发覆盖**：本次未做并发写入实证，不列为已确认故障，也不据此提前引入队列、数据库或锁服务。
- **中文同义改写召回**：关键词系统不自动理解“登录鉴权”和“身份验证怎么做”。应单列为能力边界，不能与中文字符被丢弃混为一谈。

## 5. 改善方案

### 5.1 优先修复中文检索，保持现有数据和工具接口

**建议方向：在 OKF 搜索层集成中文分词，保留既有英文与代码标识符检索。**

候选库以 [go-ego/gse](https://github.com/go-ego/gse) 为优先：Go 实现，支持中文搜索分词、简繁体和嵌入词典。它能集成进可执行程序，不需要独立分词服务。

实施要求：

1. 固定 OKF 源码版本与分词库版本，在隔离副本修改；保留原始 `okf.exe`。
2. 中文采用搜索分词；查询与文档使用一致的分词路径，保留中英文混合内容。
3. 保留原有英文、数字、概念 ID 和代码标识符的有效检索行为，避免修中文却破坏英文。
4. 对分词未收录的项目名、专有名词，评估原文子串兜底；仅在候选不足时执行，排序上明确区分精确命中与较弱匹配。
5. 词典随程序嵌入或随发行包固定提供，不依赖用户工作目录，不在日常启动时在线下载。
6. 词典只初始化一次；记录冷启动和持续查询成本，不能直接沿用旧版微秒级性能宣传。
7. 保持现有 Markdown、概念 ID 与 MCP 参数兼容，不为这次修复重写全部记忆。

中文双字切分（CJK bigram）也是可比较的轻量方案：不依赖词典，但可能增加弱相关命中。可用同一测试集与 gse 比较后选择，不预先叠加两套复杂检索系统。

**已有官方进展**：[PR #15](https://github.com/okf-memory/okf-agent-memory/pull/15) 已提出 Unicode 支持，但核查时仍为 Open。它让中文不再被丢弃，却没有中文分词；连续中文句子仍可能被当成整段词，只合入该补丁不足以宣告问题解决。

**备选库**：[gojieba](https://github.com/yanyiwu/gojieba) 支持结巴搜索分词，但有 cgo / C++ 依赖。针对本机轻量 Windows 部署，不作为第一选择。

### 5.2 简化访问：优先采用官方 CLI 显式选库

**推荐目标：Agent 负责选库，用户只提出自然语言需求。不给用户增加双 MCP 的日常负担。**

本机已有可调用的 `okf.exe`，官方 CLI 允许每次明确传入 bundle 路径，适合现有 C、D、E 跨盘布局。建议先在实际客户端验证 CLI 读写后，将它作为多库访问主路径；验证通过前不移除当前可用接入。

选库规则：

| 场景 | 应有行为 |
|---|---|
| 已明确在某个项目工作 | 用该项目的 `knowledge/`；定位依据是实际目标项目路径 |
| 查询通用偏好、跨项目约定 | 明确读全局库 |
| 当前项目没有知识库 | 报告缺库；在有授权的初始化流程中建立项目库，不把项目记录静默写进全局 |
| 明确要求跨项目检索 | 对相关库分别查询，保留项目来源；不默认扫描整台电脑 |
| 项目位置不确定 | 先根据工作上下文定位；仍无法确定时说明缺失信息，不猜测写入路径 |

CLI 也不是自动选库魔法：规则必须写清楚，Agent 必须带上正确路径。路径、引擎位置和命令由接入规则管理，不要求用户背诵。

如果以后明确要求“只能使用一个 MCP，所有读写必须经 MCP”，再评估受限的多根目录适配。它需要路径白名单、读写验证和版本维护，**不是现有官方 CLI 同等成本的配置开关，本阶段不建议额外开发**。

### 5.3 保留有用的进度约定，消除错误回退

固定进度页符合用户“问到哪就直接恢复”的使用习惯，可继续保留，但明确它是本机约定。

1. 对近期真正需要继续工作的项目补齐进度页。内容应来自已有记录、代码或用户确认；无法判断当前状态时写“待核实”，不能凭空宣布完成。
2. 不为了凑齐文件数批量编造 12 个项目的最新进度。
3. 统一 wrapper / CLI 路由与插件的项目识别依据；先确定项目库，再判断该库是否存在进度文件。
4. 项目进度缺失时明确标记缺失；不得将全局进度作为该项目进度替代。
5. 如确需注入全局内容，单列为“全局记忆”，携带来源路径，与项目进度明确分开。
6. 在库索引中建立必要的进度页关联，修复全局 orphan；更新后重新严格校验。

### 5.4 合并规则，撤掉过期方案描述

在实际改善通过验收后，同步修改客户端记忆规则、使用指南和进度记录：

- 保留一套一致的选库、查询、写入、进度恢复规则。
- 将未实施的双 MCP 文档明确标为历史候选，避免其他 Agent 误认其为当前部署。
- 移除“搜不到就是没记过”“补中文别名即可修复”“缺进度文件就是 OKF 安装坏了”等不准确结论。
- 配置改动前备份；用户未明确要求时不提交、推送或删除旧迁移源库。

## 6. 实施顺序与验收

| 阶段 | 工作 | 通过条件 |
|---|---|---|
| A：建立基线 | 备份配置、引擎，记录知识文件校验值；在副本建立固定查询集 | 数据来源和预期命中明确，能够重复比较 |
| B：检索修复 | 在隔离引擎中实现中文分词，比较必要的子串兜底 | 中文关键词缺陷消失，英文检索无明显回退 |
| C：访问简化 | 在实际使用的客户端验证 CLI 显式选库 | 跨盘读写、全局 / 项目分流及缺库行为符合规则 |
| D：进度修复 | 处理正在使用项目的进度页与压缩注入 | 进度来源正确，缺失时不串入全局 |
| E：切换与归档 | 通过验收后替换引擎、更新规则和文档 | 可回滚，真实数据未被测试覆盖，实际客户端重新加载后通过检查 |

### 6.1 检索验收集

以下是建议验收项，不是已经完成的修复结果：

| 类别 | 示例 | 预期 |
|---|---|---|
| 原文中文词 | 文档含“长期记忆已经保存在知识库中”，搜“记忆”“知识库” | 正确概念进入前 3 |
| 句中词 | 文档含“登录鉴权采用 JWT”，搜“登录”“鉴权” | 正确概念进入前 3 |
| 中英文混合 | “Unity 动画”“OKF 迁移”“JWT 过期” | 中英文均能参与匹配 |
| 项目专名 | 实际项目名称、模块名 | 可找到对应知识，标明来源 |
| 英文回归 | 既有英文 ID、模块名、缩写 | 已有有效查询不丢失目标 |
| 负例 | 库内不存在的明确主题 | 不因切词过碎产生大量高分无关结果 |
| 同义改写 | “登录鉴权”改问“身份验证怎么做” | 单独记录结果；不将语义能力作为本次关键词修复的保证 |

建议从现有全局库和代表性项目库选取至少 20 条人工标注查询，覆盖纯中文、混合词、英文、负例。查询测试只读；写入测试使用独立测试库。

性能记录冷启动、连续查询耗时与内存。对当前数百条规模，建议以本机连续查询 p95 不超过 200 ms、进程冷启动及首次查询不超过 2 s 作为初始工程目标；它们是待实测的验收目标，不是已知性能数据，不包含客户端调度和审批耗时。

### 6.2 选库与进度验收

- 在 C、D、E 各选独立测试库写入不同标识，确认读写均落在指定库。
- 项目操作不改动全局测试库，通用偏好写入不改动项目测试库。
- 在没有 `knowledge/` 的项目执行项目记忆操作时，不静默回退全局。
- 新会话与切换项目后查询来源正确；不能只测试单次命令成功。
- 项目无进度但全局有进度时，压缩恢复不得把全局内容标成项目进度。
- 分别验证实际继续使用的 OpenCode、Codex、WorkBuddy；未验证的客户端标注为待验收。
- 校验需同时看 `is_conformant` 与 `gate_passed`，不能只看格式符合就宣布严格校验通过。

### 6.3 回滚

保留原 `okf.exe`、wrapper、客户端配置、规则和插件的备份。优先保持修复前后数据格式兼容，使回滚只涉及引擎和接入文件。测试不得覆盖真实概念；若未来方案需要改写数据，应另行提供迁移与回滚步骤。本次不删除任何 MegaMemory 原始库或备份。

## 7. 其他记忆系统的位置

本节仅记录已搜索的替代方向，防止重复选型；不是本次推荐迁移。

| 候选 | 核查结果 | 暂不替换的原因 |
|---|---|---|
| [agentbrain](https://github.com/2672243194/agentbrain) | CJK bigram + BM25，Markdown + MCP；小样本源码调用能搜到“记忆”“知识库”“登录”，同义改写仍为空 | 项目标为 Beta；未做完整部署与稳定性验证，迁移收益尚不足以确定 |
| [Basic Memory](https://github.com/basicmachines-co/basic-memory) | 官方提供多语言 MiniLM 和中文 Jina 模型配置，有包含中文的小规模评测 | 需要模型与向量维护；先前英文默认模型测试不能代表中文配置，但也未证明换后更省心 |
| [mcp-memory-service](https://github.com/doobidoo/mcp-memory-service) | 支持多语言模型与混合检索；默认模型偏英文 | Python / ONNX / 模型重建增加维护成本 |
| [serradura/okf](https://github.com/serradura/okf) | 同格式另一实现，默认原文子串匹配，多库读取 | Ruby / Docker 依赖，MCP 读写能力不与现有接口等价 |

只有当需求明确升级为“中文同义改写、长文语义召回”，或局部修复成本明显超出预期时，才重新评估替换。
